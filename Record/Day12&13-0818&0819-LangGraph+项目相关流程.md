## LangGraph基础

#### State、Node、Edge
`State` 当前执行快照，例如 questionId、answer、score、round、userWantsStop。它回答“现在已知什么”。

`Node` 一个有明确职责的处理步骤：读取 State，执行评分或生成题目，再返回状态更新。它回答“这一步做什么”。

`Edge` 节点之间的控制流。普通边固定去向；条件边读取 State 后选择下一节点。它回答“下一步去哪”。

节点用来做事，可以是工具，函数等，边决定去向哪个节点，状态承载跨节点事实，就是相对的共享数据

#### 循环
对于各个节点之间的连接，会有循环的情况，对于循环的处理必须要有相应的结束标准不能一直在循环中

“评分 → 下一题 → 评分”可以构成循环，但至少要有可判定的出口，例如用户主动停止、达到最大轮数、目标能力已掌握或发生不可恢复错误。框架的递归上限是保险丝，不应代替业务终止条件。

## 项目相关

#### 面试会话完整流程
```
创建 Session
→ 获取题目
→ 保存回答并更新轮次
→ 评分并持久化评分结果
→ 计算是否结束 shouldEnd
→ 选择下一题或生成报告
→ 根据薄弱点更新学习计划
```

#### 会话状态机
| 状态 | 含义 | 合法操作 |
|---|---|---|
| `CREATED` | 会话已创建，尚未开始答题 | 获取第一题，并转为 `IN_PROGRESS` |
| `IN_PROGRESS` | 面试正在进行 | 提交当前题目的回答、获取下一题 |
| `FINISHED` | 面试已经结束 | 查询最终报告，禁止继续提交回答 |

提交回答时不能只检查会话状态，还要检查：
- 当前是否存在待回答题目；
- 当前题目是否已经提交；
- 会话是否已经结束；
- 请求是否属于同一次重复提交。


#### 事务与幂等的区别
| 机制 | 解决的问题 |
|---|---|
| 数据库事务 | 同一次请求中的多个数据库操作保持原子性 |
| 幂等机制 | 同一次业务请求被重复发送时，避免重复产生副作用 |

事务无法解决客户端超时后重新提交请求的问题，因此还需要幂等键。

#### 请求幂等设计
```JSON
客户端提交回答时携带唯一的 requestId：
{
  "requestId": "R100",
  "sessionId": "S1",
  "questionId": "Q3",
  "content": "用户回答"
}
```

如果 R100 已经成功创建回答 A17，后续收到相同 requestId 时：
- 不再创建回答；
- 不再增加 currentRound；
- 复用第一次请求的业务结果；
- 返回已有的 answerId=A17。

幂等的核心是：
>识别同一次业务操作，并复用已经产生的结果，而不是再次执行副作用。

#### 跨模块失败恢复
回答保存成功、评分调用超时时，已经保存的回答是有效业务事实，不能因为后续评分失败而删除。

恢复流程：
```
根据 answerId 查询评分结果
→ 如果评分存在，复用已有 scoreId
→ 如果评分不存在，幂等重试评分
→ 评分完成后计算 shouldEnd
→ 选择下一题或生成报告
```
评分表可以对 answer_id 建立唯一约束，防止同一回答生成多条评分记录。

#### 评分阶段状态
| 状态 | 含义 |
|---|---|
| `ANSWER_SAVED` | 回答已持久化 |
| `SCORING` | 评分正在处理或结果未知 |
| `SCORED` | 评分已经完成并持久化 |

评分超时并不代表评分一定失败，而是结果未知。因此恢复时必须先查询，不能直接再次调用模型

#### 模块数据所有权
- 会话模块：拥有 Session、回答、轮次等数据。
- 评分模块：负责生成并持久化评分结果。
- 学习计划模块：消费薄弱点并更新学习计划。
- Agent：负责调用公开 API、保存跨步骤引用和进行流程编排。
Agent 不应直接修改其他模块的内部数据库表。

#### Checkpoint 与业务数据
Checkpoint 只保存流程恢复所需的信息，例如：
```
当前执行步骤
answerId
scoreId
重试次数
等待状态
剩余轮次
```
回答、评分、会话等业务结果仍由对应业务模块持久化。
>Checkpoint 用于恢复流程，不是业务数据库的替代品。


## MVCC
MVCC(多版本并发控制)，是一种数据库并发控制机制，主要是通过保存数据的历史版本，实现读写不互相阻塞，可以提升数据库在高并发场景下的性能

- 核心目标:解决并发场景下的读写阻塞问题，实现“读不加锁，读写并行”
- 解决的问题:主要解决读-写并发下的隔离性问题(如脏读、不可重复读、幻读)，但不能解决更新丢失(脏写)问题，后者需要依赖锁机制(悲观锁或乐观锁)
- 实现方式:通过undo_log(回滚日志)保存数据的历史版本，配合ReadView(读视图)判断当前事务可见的版本，从而在快照读时无需加锁即可获得一致性的数据视图

### 底层原理/深入解析
MVCC 的实现并非在数据库中实际存储多份完整的数据副本，而是通过 undo log + ReadView + 隐藏字段（trx_id、roll_pointer） 三者协同完成的。

#### 数据行的隐藏字段与版本链
InnoDB 存储引擎中，每一行记录除了用户定义的字段外，还包含两个隐藏字段：

- trx_id：记录最近一次修改该行数据的事务 ID。
- roll_pointer：指向该行记录在 undo log 中对应的旧版本记录，形成一条版本链。

当执行 UPDATE 操作时，InnoDB 不会直接覆盖旧值，而是：

1.将修改前的旧值（以及 trx_id、roll_pointer）写入 undo log。

2.新版本的行记录中的 roll_pointer 指向 undo log 中的旧版本。

3.新版本的 trx_id 更新为当前事务 ID。

这样，每次更新都会在版本链上追加一个新节点，链头永远是最新版本，链尾是最早的版本。
>类比：想象一本图书的修订记录，每次修改不是撕掉旧页，而是在旧页上叠加一张半透明的新页，并记录“这页是谁改的、上一页在哪”。读者（事务）可以根据自己的权限选择看哪一层的内容。

#### ReadView（读视图）的可见性判断
`ReadView`是MVCC判断“当前事务能看到哪个核心版本”的核心。它主要包含以下关键信息：

- m_ids：生成 ReadView 时，当前系统中活跃（未提交） 的事务 ID 列表。
- min_trx_id：m_ids 中的最小值（最早活跃事务）。
- max_trx_id：生成 ReadView 时，系统分配给下一个事务的 ID（即当前最大事务 ID + 1）。
- creator_trx_id：生成该 ReadView 的事务自己的 ID。

**可见性判断规则**（针对版本链上的某个版本的 `trx_id`）：

| 条件                                  | 可见性 | 原因                                                                |
| ------------------------------------- | ------ | ------------------------------------------------------------------- |
| `trx_id == creator_trx_id`          | 可见   | 自己修改的数据，当然可见                                            |
| `trx_id < min_trx_id`               | 可见   | 该版本在 ReadView 生成前就已提交，必然可见                          |
| `trx_id >= max_trx_id`              | 不可见 | 该版本是 ReadView 生成后开启的事务修改的，不可见                    |
| `min_trx_id <= trx_id < max_trx_id` | 需判断 | 若 `trx_id` 在 `m_ids` 中（活跃），不可见；否则（已提交），可见 |

**核心逻辑**：顺着 `undo log` 版本链从最新版本往回找，找到第一个满足可见性规则的版本，即为当前事务快照读的结果。

####  隔离级别与 ReadView 的生成时机

MVCC 的可见性行为与隔离级别强相关，关键在于 ReadView 的生成时机 [S4]：

* **读已提交（Read Committed）**：**每次执行快照读（`SELECT`）时都会生成一个新的 ReadView**。这意味着同一事务内多次查询可能看到不同的数据（其他事务已提交的新版本），导致不可重复读。
* **可重复读（Repeatable Read）**：**事务第一次执行快照读时生成 ReadView，之后整个事务内复用该 ReadView**。后续查询始终基于同一视图，因此看到的数据始终一致，解决了不可重复读问题。

> 注意：MVCC 只解决快照读下的幻读问题。对于当前读（`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE`），InnoDB 使用 **Next-Key Lock（临键锁）** 来防止幻读，这是另一套机制。

#### MVCC 与锁的协作

MVCC 并非万能的，它擅长解决**读写冲突**，但无法处理**写写冲突**（更新丢失）。因此实际生产中通常采用组合策略：

* **MVCC + 悲观锁**：MVCC 解决读写并发，悲观锁（如 `SELECT ... FOR UPDATE`）解决写写并发。
* **MVCC + 乐观锁**：MVCC 解决读写并发，乐观锁（版本号、CAS）解决写写并发。

#### 为什么 MVCC 不能解决更新丢失？

更新丢失（Lost Update）发生在两个事务同时基于同一旧值进行修改，后提交的一方覆盖先提交的一方的修改。MVCC 的快照读只保证**读取**的一致性，但**写操作（当前读）** 是基于最新版本进行的，若两个事务同时读到旧版本并更新，后提交者会覆盖前者。这需要依赖锁（悲观锁）或重试机制（乐观锁）来规避。

**MVCC 能解决幻读吗？**

> 回答思路：分场景。在**快照读**下，可重复读级别通过复用 ReadView 解决了幻读（因为整个事务只看到一个固定快照）。但在**当前读**下（`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE`），MVCC 无法解决，需要依赖 **Next-Key Lock（记录锁 + 间隙锁）** 来锁定范围，防止新记录插入。MySQL 默认的可重复读级别下，当前读 + Next-Key Lock 能完全解决幻读。

**ReadView 中的 `max_trx_id` 具体怎么理解？**

> 回答思路：`max_trx_id` 不是“当前最大活跃事务 ID”，而是“生成 ReadView 时，系统已分配的最大事务 ID + 1”。它代表一个**边界**：任何事务 ID 大于等于 `max_trx_id` 的版本，都是 ReadView 生成之后才开始的，对当前事务不可见。这样设计是为了避免在判断可见性时遍历所有事务，提高效率。

**为什么读已提交级别每次查询都生成新的 ReadView，而可重复读只在第一次生成？**

> 回答思路：这是两种隔离级别的语义差异。读已提交要求“只能读到已提交的数据”，因此每次查询时，之前活跃但现已提交的事务应变为可见，所以必须重新生成 ReadView 以反映最新提交状态。可重复读要求“事务内多次读取结果一致”，因此锁定第一次查询时的快照，后续复用同一 ReadView，保证一致性。

**undo log 会一直保留吗？什么时候清理？**

> 回答思路：不会永久保留。`undo log` 中的历史版本在**没有任何事务的 ReadView 还需要引用它们**时，就可以被清理。InnoDB 有一个后台线程（purge 线程）负责定期清理不再需要的 undo 记录。但如果有长事务持有旧 ReadView，会导致 undo log 无法及时清理，可能造成 undo log 膨胀，这也是长事务需要避免的原因之一。

**MVCC 与版本号（乐观锁）有什么区别？**

> 回答思路：MVCC 是**数据库内部机制**，对应用透明，由 InnoDB 自动维护版本链和 ReadView；乐观锁是**应用层实现**，需要开发者手动在表里加版本号字段，在更新时通过 `WHERE version = ?` 或 CAS 判断。MVCC 解决读写并发，乐观锁解决写写冲突。两者可以共存：MVCC 保证快照读一致性，乐观锁保证更新不丢失。

**在可重复读级别下，MVCC 的 ReadView 是事务开始时生成，还是第一次 SELECT 时生成？**

> 回答思路：准确说是**第一次执行快照读（SELECT）时**生成，而不是事务 `BEGIN` 时。如果事务只执行写操作（当前读），不会生成 ReadView。这一点在源码中体现为 `trx->read_view` 在第一次 `SELECT` 时被创建并缓存。不过对于大多数业务场景，这两种理解差异不大，但面试时能答出准确时机是加分项。
